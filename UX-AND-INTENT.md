# RFQ Markets — trading UX and intent specification

2026-09-08. Current product specification for the normal market-order flow. Protocol fields are generated by the application; they are not separate fields in the trading form.

## Default interface

The trading ticket exposes market, Buy/Sell, amount and the live estimated result. The primary interaction is:

1. Select BTC or ETH.
2. Enter notional or underlying amount.
3. Observe the continuously updated estimated execution price, fee, position/margin result and liquidation estimate.
4. Click Buy or Sell once.

The confirmation area should show one prominent estimate and a compact protection line such as `Estimated 65,120 · worst accepted 65,185 · fee 0.04%`. The user does not type an oracle, nonce, deadline, fee cap, receiver, contract, chain, signer version or leader epoch.

Advanced settings contain maximum slippage, default order lifetime, reduce-only and optional session controls. They are saved per browser/account. The main ticket surfaces a changed or unusually wide protection rather than hiding it.

## Market-with-protection semantics

The continuously displayed quote is indicative and reserves no maker capacity. Clicking Buy/Sell creates an executable user intent. The expected execution may move before settlement, but the contract cannot execute beyond the signed maximum buy price/minimum sell price or fee cap.

The client calculates the default adverse-price bound from the displayed quote and a signed application policy:

`autoTolerance = clamp(8 bps, 50 bps, p99 measured click-to-inclusion move + current short-horizon volatility buffer)`

The numerical 8/50 bps bounds are initial BTC/ETH test parameters, not proven production values. The browser applies the smaller of the policy result and the user's saved maximum. The API cannot widen it. If the market moves beyond it, the trade expires/rejects and the UI offers the new price; it never silently changes the user's limit.

Default user-intent lifetime is 15 seconds. Maker approvals are exact-fill authorizations with a 3-second maximum lifetime and an oracle-observation age limit specified by the oracle mode. The API may obtain a fresh approval within the original user intent without another prompt. It may not extend the 15 seconds or change the user's economic bounds.

The API does not return reusable maker approvals to the browser in the normal flow. It submits an approved bundle immediately. Anyone may technically submit a valid bundle if it escapes, so correctness still depends on contract nonces, expiry and current-state checks.

## Generated signed intent

The client constructs and signs:

| Field | Source |
| --- | --- |
| account/subaccount and receiver | Connected account and selected subaccount |
| market and side | Trading ticket |
| exact size | Amount input, normalized to contract units |
| limit price | Live quote plus automatic/saved protection |
| maximum total fee | Displayed fee plus no hidden increment; explicit cap |
| deadline | Current time plus the selected 15-second default |
| nonce | Contract/account nonce read through the live state service |
| reduce-only | Position context or advanced user selection |
| partial-fill policy | `none` in v1 |
| chain and verifying contract | Pinned application deployment manifest |
| intent schema/policy version | Pinned application deployment manifest |

Use EIP-712 typed data and implement replay protection in the clearing contract; [EIP-712 does not itself provide replay protection](https://eips.ethereum.org/EIPS/eip-712).

## Click and signing experience

Baseline compatible mode: clicking Buy/Sell opens the connected wallet's readable typed-data confirmation. This is one click in the application plus the wallet confirmation.

Optional fast mode: the owner performs a one-time wallet authorization for a locally generated session key. Subsequent Buy/Sell clicks sign intents locally without wallet popups. The contract, rather than only the frontend, enforces:

- specific account and clearing contract;
- trade-only selectors, with no withdrawals or delegation changes;
- allowed markets;
- maximum single-trade notional;
- rolling gross turnover and maximum resulting exposure;
- maximum fee and slippage;
- expiration no longer than 24 hours by default;
- owner revocation and account-wide emergency nonce invalidation.

The local prototype keeps its random session private key in tab-scoped `sessionStorage` and dynamically loads the signing code only after opt-in. This is useful for end-to-end testing, but a script running in the origin can read it. Production requires a strict content-security policy, no unreviewed third-party scripts, and non-exportable browser/device storage or a wallet-provider session mechanism where supported. Treat browser compromise as capable of losing the entire remaining session allowance. Wallet permission/session mechanisms are still wallet-dependent rather than universally standardized, as the [ERC-4337 session-key documentation](https://docs.erc4337.io/smart-accounts/session-keys-and-delegation.html) notes. ERC-7715 remains a compatibility option, not a required v1 dependency.

The implemented local flow uses an owner-signed EIP-712 grant sponsored as a separate activation transaction. The grant binds owner/account, session public key, allowed markets, single/cumulative notional, fee cap, expiry and shared owner nonce. Direct owner revocation is implemented; sponsored revocation and lazy first-trade activation require either contract headroom from further modularization or account-abstraction support.

## Deposits, withdrawals and gas

For a compatible native USDC deployment, the user signs an exact-amount, short-lived EIP-3009 transfer authorization or EIP-2612 permit; the API sponsors one atomic clearing-contract deposit transaction. Do not request an unlimited allowance. Circle's reference FiatToken design documents both signed authorization methods and ERC-1271 validation. Verify the deployed Base USDC proxy implementation, domain separator and smart-wallet behavior before enabling this route. [Circle FiatToken design](https://github.com/circlefin/stablecoin-evm/blob/master/doc/tokendesign.md).

Fallback onboarding is an ordinary exact approval followed by deposit. Existing sufficient allowance allows a sponsored deposit. ERC-4337/paymaster onboarding is an optional wallet integration rather than a protocol dependency.

Withdrawals use an owner-signed exact amount, receiver, nonce and deadline; the API may sponsor submission but cannot alter it. Session keys can never withdraw. Users retain direct owner-paid deposit, cancellation, revocation, exit and withdrawal calls if the API is unavailable. Thus normal trading and supported onboarding can be gasless to the user, while no chain operation is described as literally gas-free.

## Order states

The user sees: `Preparing` -> `Submitted` -> `Executed` -> `Settled`. `Submitted` means the transaction was accepted for propagation; `Executed` may use Base preconfirmation; `Settled` means the selected sealed/finality checkpoint. A failure shows one reason: price protection, insufficient margin, capacity, oracle unavailable, expired, cancelled or network failure.

Base's Flashblocks interfaces expose pending-state simulation and transaction signals at approximately 200 ms intervals, which can support the `Executed` UI state without pretending it is irreversible. [Base Flashblocks overview](https://docs.base.org/base-chain/api-reference/flashblocks-api/flashblocks-api-overview).

## Reservations and different addresses

Indicative quote requests from any number of addresses do nothing to inventory. Only a signed executable click enters admission.

After click A is admitted, its possible exposure is recorded before remote calls begin. Click B, from the same or another address, is evaluated against every materially possible state of A: A executes or A does not execute. B receives the least favorable maker-safe price across those possibilities. Therefore:

- if A and B increase risk in the same direction, B pays for the possibility that A executes first;
- if B would offset A, B receives no discount that depends on A executing;
- if A has already executed, B can receive the real inventory-reduction price;
- if A becomes conclusively impossible, its reservation is removed and new quotes improve immediately.

The system does not need to know the addresses are related. This conservative pricing can make B slightly worse if A later fails, which is why admitted intents are submitted immediately and kept short. A future atomic dependent bundle could improve this, but is excluded from v1.

There is no normal user action called “abandon” after clicking a market order. The residual optionality comes from API/network failure, on-chain cancellation racing execution, expiry, leaked approvals or malicious infrastructure. Reservations and contract checks cover those cases.
