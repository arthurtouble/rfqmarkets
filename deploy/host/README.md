# Persistent financial runtime

The host launcher supports explicit `base-sepolia` and `base-mainnet` profiles. Each profile is bound to its exact chain, official USDC address and Hyperliquid environment; a Sepolia configuration cannot select production endpoints. Mainnet execution remains gated by candidate-bound release evidence, qualification and independent reviews. Cloudflare Containers are disabled because their disk cannot retain financial journals.

Provision a Linux host with Node 24, a mounted encrypted persistent filesystem at `/var/lib/rfq`, and one service user and directory per role. Put reviewed immutable code in `/opt/rfq`. Each host starts one signer identity; provision the three approvers on separate hosts/accounts with separate operators. Each service receives only its role secret file, owned by its service user, mode 0600. API configuration contains bearer credentials and must also be private. Never distribute bootstrap identity bundles or governance keys. `Dockerfile.host` pins its Linux amd64 Node base manifest and installs the complete Python venue graph from a hash-locked wheel set. Record the resulting image digest and SBOM in release evidence; the Dockerfile remains a build input, not a signed release image.

`rfq@.service` supplies a local exclusive writer lock, filesystem isolation and bounded stop time. This protects against duplicate processes on one volume; it is not a multi-host lease. For failover, fence the old host and revoke its sponsor/venue agent authority before starting a recovered writer. A host whose death cannot be proven remains fenced; do not run active-active financial writers. The container entrypoint requires an externally held equivalent lock and a persistent bind mount; loopback listeners require a sidecar in the same network namespace. Native systemd is the initial recommended profile.

Configuration for `scripts/persistent-service.ts ROLE CONFIG SECRET` must include: environment (`base-sepolia` or `base-mainnet`), its matching chainId (`84532` or `8453`), rpcUrl, secondaryRpcUrl, clearingAddress, the profile's official tokenAddress, stateDirectory=/var/lib/rfq/ROLE, port, startBlock, publicRpcUrl, corsOrigin, hedgeRiskUrl, indexerUrl, apiUrl, feedIds=[BTC,ETH], hedgeBandUsdc, hedgeMaxOrderUsdc, hedgeMinOrderUsdc. RPC URLs must use HTTPS. Hedge amounts are positive integer six-decimal USDC units. API additionally requires three approvers with URL/token. Secrets: API sponsorKey/oracleKey/operationsToken/dailyBudgetWei/maxFeePerGas/maxOracleValueWei (budget values are integer wei); approver privateKey/transportToken/hedgeToken; hedger agentKey/accountAddress/agentName/operationsToken; read roles use `{}`. The entrypoint rejects unrelated secret fields and checks RPC chain, deployed proxy/token, and signer membership. External secondary RPC failure/domain isolation and feed/implementation identities must also be checked during deployment review.

The independent `keeper` role uses separately provisioned sponsorKey/oracleKey/operationsToken/dailyBudgetWei/maxFeePerGas/maxOracleValueWei. Give it its own host user, journal, funded sponsor and writer lock; do not reuse the API sponsor. See [keeper behavior and qualification](../../services/keeper/README.md).

Every role configuration now also requires `runtimeIdentity`: oracleAddress, oracleSource, governance, emergencyCouncil, implementationAddress, riskMathAddress, signatureVerifierAddress, approvers=[three reviewed distinct addresses], and code=[{address,hash}] for proxy/token/adapter/oracle source/implementation/both linked modules. Hashes are keccak256 of actual deployed runtime bytecode, including immutable/link substitutions. Startup checks both RPCs at the same block/hash, the EIP-1967 implementation slot, exact token decimals, adapter/feeds, authorities/signer set, every listed code hash and embedded linked-module addresses. API/keeper configurations additionally require sponsorAddress matching their separately provisioned key; a governance/emergency/approver address cannot be a sponsor.

`node --import tsx scripts/observe-runtime-identity.ts DEPLOYMENT_MANIFEST` with RFQ_BASE_SEPOLIA_RPC_URL and RFQ_SECONDARY_RPC_URL produces an observed identity for review. Observation checks consistency but does not prove code corresponds to audited source; compare compiled linked/immutable bytecode, authority custody and approved chain/feed registry independently before adopting these values. The observer never authorizes mainnet.

Expose only the public route allowlist through an authenticated private Tunnel/origin. Configure Cloudflare Access for admin/operations and private approver transports; no direct public ports. Do not trust arbitrary forwarded IP headers. Supply service bindings or a reviewed origin bridge for the public edge; the repository's static worker configuration has no provisioned runtime bindings.

## Backup and restore drill

1. Pause new admission; record leader epoch, finalized block/hash, all unresolved operations and venue order IDs. Stop the role writer and acquire its exact `writer.lock`. Repeat for each independently provisioned signer; retain every escaped approval and sender/venue attempt. An indexer snapshot alone cannot recover commitments.
2. Create a mode-0600 context file containing the exact environment, chain ID, clearing address, role, writer address (for signing roles), and frozen candidate hash. Under the lock run `node --import tsx scripts/journal-snapshot.ts /var/lib/rfq/ROLE/ROLE.sqlite SNAPSHOT_DIRECTORY CONTEXT_JSON`. It performs SQLite integrity validation and a consistent snapshot, then binds its checksum and byte length to that role/deployment/candidate context. Keep the full snapshot directory; encrypt before copying off-host. Signed raw transactions and approvals are sensitive despite containing no private keys.
3. Under the destination role's `writer.lock`, run `node --import tsx scripts/journal-restore.ts SNAPSHOT_DIRECTORY /var/lib/rfq/ROLE/ROLE.sqlite EXPECTED_CONTEXT_JSON`. It requires an exact context match, verifies checksum, length, and SQLite integrity before and after a mode-0600 atomic install, and refuses to overwrite any journal. Restore reviewed configuration independently from secrets. Never generate an empty commitment journal to repair startup.
4. After capturing API, all three approvers, indexer, hedger, and keeper, run `npm run evidence:backup-set -- OUTPUT_JSON MANIFEST_JSON...`. The evidence command rejects missing roles, repeated signing identities, and manifests from another chain, clearing deployment, or candidate. Feed the same seven manifests to the operational snapshot collector; backup freshness is measured from the oldest required role.
4. Fence old writers before recovery. Reconcile chain receipts, approver epochs/expiry, canonical included/finalized block hashes, venue client IDs and positions. Any unresolved nonce or order ambiguity keeps readiness closed. Advance the leader epoch through the authorized ceremony if required; retained unexpired commitments remain conservative until proven expired/fenced.
5. Test response loss before/after submission and kill/restart on the restored testnet candidate. Compare receipts, customer balances and venue IDs. Record RPO/RTO and encrypted backup location in the release evidence. Off-host restore qualification is still pending.

Rollback means restoring an audited implementation through the timelock and checking storage/capital; a filesystem snapshot does not rewind chain or venue state. Never overwrite newer financial journals with an older snapshot while retaining the same signing authority.

## Repairing incomplete signer payloads

An authenticated `/internal/recovery` export includes signatures and private complete payloads. Save it with permissions 0600. After fencing the signer and holding its writer lock, `node --import tsx scripts/import-approver-recovery.ts JOURNAL PRIVATE_EXPORT CHAIN_ID PROXY SIGNER` can import verified payloads into that identity's existing journal. It validates domain, intent/approval hashes, signature, epoch and exact signed expiry, preserves maximum gross reservations, rejects conflicts and commits atomically. It does not import an export's claimed finalized clock or remove existing records. Missing payloads remain explicit in the result and signer readiness.

This repairs known payload loss; it does not prove an export contains every escaped signature or replace a complete snapshot/fencing ceremony. An empty or stale export is never evidence that a reused signing authority has no outstanding commitments. The API now reconstructs complete active signed retry envelopes from a restored journal and fails readiness when an active artifact is partial or inconsistent. Finalized expired API and signer records move to archive tables without releasing risk early. Encrypting and retaining snapshots/archive exports off-host and qualifying the clean-host ceremony remain operator evidence gates.
