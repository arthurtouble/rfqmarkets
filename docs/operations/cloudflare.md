# Cloudflare hosting

Everything except the contracts runs on the RFQ Markets Cloudflare account: the apps, the public edge, the backend services and the three oracle nodes. It is the Base mainnet dev environment, and it is the only hosted environment. The step-by-step setup, keys and day-to-day commands are in [deploy/cloudflare/DEV-ENVIRONMENT.md](../../deploy/cloudflare/DEV-ENVIRONMENT.md). This page covers what is deployed, how a deploy works, what the edge does and what the deploy needs.

This is a development layout. It must not hold customer funds. Production financial services move to persistent hosts (see [Production direction](#production-direction)).

## What is deployed

| Worker | What it serves | Access |
| --- | --- | --- |
| `dev` | Trading app (`apps/web`) and the public edge for service routes (`deploy/cloudflare/static/web-edge.mjs`) | Public, `https://dev.rfq-markets.workers.dev` |
| `docs` | Public docs (`apps/docs`), static assets only | Public, `https://docs.rfq-markets.workers.dev` |
| `exit` | Direct exit page (`apps/exit`), built for the dev clearing address | Public |
| `admin` | Hedge operations dashboard (`apps/admin`) | Cloudflare Access |
| `internal-docs` | This manual (`apps/internal-docs`) | Cloudflare Access |
| `rfq-markets-runtime-dev` | One container running the API, three approvers, indexer, stream gateway and simulated hedger (`deploy/cloudflare/runtime/dev-worker.mjs`) | No public route. Reached only through service bindings. |
| `oracle-1`, `oracle-2`, `oracle-3` | One oracle node container each (`deploy/cloudflare/runtime/oracle-worker.mjs`), placed near `wnam`, `weur` and `apac` | Public, GET only, rate-limited |

State lives in the `rfq-markets-dev-state` KV namespace: the contract deployment record (`deployment.json`), the published runtime and oracle addresses, the owner key and the last deployed commit (`deployed-commit`). Keys generated by the runtime and the oracle nodes stay in their Durable Objects. The runtime's cron runs every minute to keep the container up and save a journal snapshot.

## Deploy

`.github/workflows/deploy-cloudflare-dev.yml` runs after every successful `CI` run on `main`, or by manual dispatch on `main`. It deploys only when the CI run came from a push to this repository's `main`; a fork's own `main` branch does not qualify. It skips with a notice if the Cloudflare secrets are missing. The job runs `npm ci` and then `scripts/cloudflare-dev-deploy.sh`.

The script works the same from any machine with Docker, Node and a Cloudflare token. In order, it:

1. Finds or creates the KV namespace and reads `deployment.json`, if contracts exist.
2. Builds the trading app with `VITE_CHAIN_ID=8453` and, once contracts exist, the clearing and USDC addresses from the deployment record. The app then refuses a `/v1/config` that names other contracts. Redeploy the app after a contract redeployment.
3. Builds the docs (with `DOCS_SITE_URL` set to the docs Worker), the dashboard and the internal docs, then runs `npm run validate:cloudflare-static`.
4. Runs `scripts/cloudflare-oracle-deploy.sh`. It builds the oracle image once and deploys the three nodes one at a time. After each one it waits up to 300 seconds (`RFQ_ORACLE_ROLLOUT_TIMEOUT`) for `/health` to answer 200, or 503 because it is waiting for a deployment that names it. Anything else stops the rollout, so a bad build reaches one node at most.
5. Builds and pushes the runtime image (`deploy/cloudflare/Dockerfile.dev`), writes the `RFQ_DEV_RUNTIME_SECRETS` Worker secret (RPC URLs and the oracle node URLs), then deploys the runtime. The secret goes first because the runtime reads it only at start.
6. Deploys the `dev` and `docs` Workers.
7. Deploys `admin` and `internal-docs` after `scripts/cloudflare-access.mjs` has made sure each has an Access application.
8. Builds and deploys the exit page once a clearing address exists.
9. Records the commit in KV `deployed-commit`.

The dev deploy ships the docs Worker. The separate testnet docs workflow and the Base Sepolia testnet are gone.

Contracts are not deployed by this workflow. `.github/workflows/dev-contracts.yml` deploys, upgrades and operates them. Each run needs approval in the `mainnet-dev` GitHub environment. See [Base mainnet deployment](base-mainnet.md).

### Rollback

A failed Worker deploy cannot change contracts, caps or positions. To roll back an app, redeploy the previous commit or pick the previous Worker version in Cloudflare. A new runtime version restarts the container, and the journals come back from the Durable Object's last snapshot.

## Secrets and variables

The deploy workflow reads these from the repository:

| Name | Kind | Purpose |
| --- | --- | --- |
| `CLOUDFLARE_API_TOKEN` | Secret | Deploys everything. Required. |
| `CLOUDFLARE_ACCOUNT_ID` | Secret | The account to deploy to. Required. |
| `RFQ_BASE_MAINNET_RPC_URL` | Secret, optional | Calls and transactions. Default `https://base-rpc.publicnode.com`. |
| `RFQ_BASE_MAINNET_SECONDARY_RPC_URL` | Secret, optional | The approvers' second RPC. Default `https://base.drpc.org`. |
| `RFQ_BASE_MAINNET_READ_RPC_URLS` | Secret, optional | Comma-separated RPCs for continuous reads. Default publicnode, then Tenderly's public gateway. |
| `RFQ_BASE_MAINNET_INDEXER_FALLBACK_RPC_URLS` | Secret, optional | Comma-separated archive RPCs for indexer catch-up. Default Tenderly's public gateway. |
| `CLOUDFLARE_WORKERS_SUBDOMAIN` | Variable, optional | The account's `workers.dev` subdomain. Default `rfq-markets`. |
| `WALLETCONNECT_PROJECT_ID` | Variable, optional | Passed to the app build as `VITE_WALLETCONNECT_PROJECT_ID`. |

The script also reads `RFQ_BASE_MAINNET_INDEXER_RPC_URL` and `RFQ_BASE_MAINNET_MAX_LOG_RANGE` (default 1,000 blocks), but the workflow does not pass them, so CI deploys use the defaults. Alchemy is not used. Behind a TLS-intercepting proxy, set `RFQ_DOCKER_BUILD_CA` to the proxy's CA bundle. If Docker Hub rate-limits, `RFQ_DOCKER_NODE_IMAGE` swaps in a mirror of the Node base image.

The account needs Workers Paid, because Containers require it. The API token needs:

- the "Edit Cloudflare Workers" template permissions;
- *Account → Containers → Edit*;
- *Account → Access: Apps and Policies → Edit* and *Account → Access: Organizations, Identity Providers, and Groups → Read*, for the private pages. Without these the deploy warns and the private pages stay locked.

No approver, sponsor, oracle or owner key goes into GitHub or a build. The runtime and the oracle nodes generate their own keys.

## The public edge

`web-edge.mjs` runs in front of the trading app. Every request goes through it.

- **Routing.** Exact path and method allowlists send reads and writes to three service bindings: `API`, `INDEXER` and `MARKET_GATEWAY`. In dev all three point at the runtime Worker. Any other path under `/v1/` or `/internal/`, and `/approve`, gets 404 `route_not_allowed`. Paths under `/ops/` are never forwarded. Non-service requests other than GET and HEAD get 405.
- **Fail closed.** A missing binding returns 503 `service_unavailable`. An upstream exception returns 503 `upstream_unavailable`. Neither falls through to an HTML page. Each proxied request carries an `x-request-id` (the `cf-ray` value when there is one).
- **Rate limits.** Before forwarding, `edge-admission.mjs` checks a per-client limit keyed on `cf-connecting-ip` and a global limit: 600 reads and 120 writes per client per minute, and 12,000 reads and 2,400 writes in total per minute. A request without a client IP gets 403. A missing or failing limiter gets 503. The runtime Worker applies the same check again. Cloudflare's counters are approximate and local to each Cloudflare location, so the services keep their own limits as well.
- **Health.** `/edge/health` reports which bindings are present. It does not claim the runtime is healthy.
- **Headers.** Responses from static assets get the app's CSP, HSTS, frame denial, no-sniff, referrer and permissions policies. They mirror `apps/web/public/_headers`, which Cloudflare does not apply to responses that pass through a Worker.

### Jurisdiction blocking

The edge checks location before rate limiting or forwarding. It reads only `request.cf.country` and `request.cf.regionCode`, which Cloudflare sets. A client-sent `cf-ipcountry` header changes nothing.

| Location | Service reads | Opening risk | Exits (close, cancel, withdraw, session, nonce cancel, settling close quotes) |
| --- | --- | --- | --- |
| Sanctioned country or occupied Ukrainian region | 451 | 451 | 451 |
| Restricted country, Tor (`T1`), unknown (`XX`) or no location | Allowed | 451 | Allowed |
| Anywhere else | Allowed | Allowed | Allowed |

Refusals are 451 with `{error: "jurisdiction_restricted", status, message}`. `GET /edge/geo` returns `{status, country, region, message}` so the app can show a full-page notice or a close-only banner. The app's check is only for display. The edge enforces the policy on every call.

The lists are in `deploy/cloudflare/static/jurisdictions.mjs`. The public policy in `apps/docs/content/legal/restricted-jurisdictions.md` must match, and `jurisdictions.test.mjs` fails if it does not. The docs and the exit page are not geo-blocked. `/edge/health` is never geo-blocked. When you test from a restricted location you get close-only mode, so run trading smoke tests from somewhere else.

## Private pages

The hedge dashboard and the internal docs each sit behind a Cloudflare Access application. Members of the RFQ Markets Cloudflare account sign in with their Cloudflare login. Their Worker (`deploy/cloudflare/static/private-edge.mjs`) also checks the Access token on every request, assets included, against the application's audience tag. If Access is missing or misconfigured, the page stays locked rather than going public.

`scripts/cloudflare-access.mjs` creates the application on the first deploy and passes the team domain and audience tag to the Worker. An existing application keeps its policy. Change who may sign in under Zero Trust → Access → Applications.

The private Worker allows only GET and HEAD. The dashboard reads the indexer's risk view and update stream, the API's config and the hedger's status through the runtime binding. The runtime adds the hedger's operations token, which it keeps in its Durable Object, so the browser never sees it. Private pages are sent with `cache-control: private, no-store`.

## Tests

- `npm run test:cloudflare-edge` covers routing, body and request-ID passthrough, missing bindings, rate limits, jurisdictions, Access checks and the runtime and oracle Workers.
- `npm run validate:cloudflare-static` checks the built apps: security header files, no loopback service URLs in the trading bundle, no inlined fonts the CSP would block, and pre-rendered docs pages with canonical links, a sitemap, `robots.txt` and `llms.txt`.

## Production direction

The dev layout puts the approvers, their keys and the oracle nodes on one Cloudflare account, and keeps journals on ephemeral container disk with a snapshot every minute. Neither is acceptable for real capital. Production keeps Cloudflare for the apps, the public edge and streaming fan-out, and moves the API, approvers, keeper, indexer and hedger to persistent hosts with separate providers and operators ([deploy/host/README.md](../../deploy/host/README.md)). The three approvers must not share one Cloudflare account, and the hedge key stays out of edge workloads. The remaining steps are in the [implementation plan](../release/implementation-plan.md).
